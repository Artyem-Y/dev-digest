# Eval Pipeline

**ID:** SPEC-2026-10-31-eval-pipeline  
**Status:** implementation basis (user authorized the plan on 2026-10-31)  
**Sources:** L06 homework and its six supplied interface screenshots; [implementation plan](../plans/2026-10-31-eval-pipeline.md).

## Purpose and scope

An agent owner turns actual reviewed findings into a dataset, evaluates an agent against fixed inputs, and compares measured results across configurations. This specification covers the product eval pipeline across server, reviewer-core, client, and browser tests. Agent export is outside scope because the supplied task does not define its behavior.

## Acceptance criteria

- **AC-1:** When a user chooses “Turn into eval case” on an accepted or dismissed finding, the system creates a case for the producing agent with `must_find` or `must_not_flag`, respectively. An undecided finding is ineligible. Repeating the action must not silently duplicate a case.
- **AC-2:** Persist the original diff fragment for the finding file, its hash, decision, source identity and anchor. Prove that the full diff matches the fingerprint recorded at review time; when the original is unavailable or unverified, explain that case creation is unavailable. Case snapshots remain unchanged when the original finding changes.
- **AC-3:** A user can inspect the agent's cases and explicitly start an evaluation of the full set. Admission snapshots the case set, system prompt, model, provider, skills, strategy and all other included inputs. Each run has a persisted identity, status, results and dataset fingerprint; changing a case or agent later does not alter history.
- **AC-4:** The evaluator matches the exact normalized file path and intersecting inclusive line ranges, using grounded findings. A `must_find` match passes the positive case; a `must_not_flag` match fails the negative case. Duplicate matching findings count at most once for the case. Findings outside the labeled anchor are counted as unlabeled and are not assumed to be correct or incorrect.
- **AC-5:** For completed cases, recall is matched positive cases divided by positive cases; labeled precision is matched positive cases divided by matched positive cases plus negative cases flagged; citation accuracy is grounded findings divided by all findings presented to the grounding gate. Zero denominators are unavailable, not zero or 100%. The UI identifies precision as restricted to labeled findings and displays its counts. Scoring makes no model call.
- **AC-6:** A failed or interrupted case is visible as such. Incomplete runs cannot appear successful or silently contribute partial data to comparable complete-run metrics. Unknown cost remains unavailable. Bounded work, timeout and recovery behavior must be documented and tested.
- **AC-7:** The agent Evals tab displays cases, latest results, run action and history. The Eval Dashboard displays agents and recent runs; the agent view displays metrics, trends and run history. All screens support loading, empty, error, running, failed, and unavailable-value states.
- **AC-8:** When two runs are selected, the comparison shows their immutable configuration and metric values. The UI identifies changes in prompt, model and skills, and warns when dataset fingerprint, engine or scorer differs; incompatible runs have no implied comparable delta.
- **AC-9:** All reads and actions enforce workspace scope on the server. Snapshots exclude credentials and raw provider responses; logs must not expose source or prompt content. UI controls are keyboard accessible and preserve focus across dialogs.
- **AC-10:** Acceptance evidence includes at least eight cases created from actual accepted/dismissed findings, an observed comparison with changed system prompt, and a deliberately degraded prompt whose observed precision decreases. The user receives a screenshot and measured counts. A fixture provider can prove data flow but cannot establish this real-model behavior.
- **AC-11:** `pnpm verify:l06` runs the repository's documented deterministic gate: scoped unit, PostgreSQL, typecheck and hermetic browser checks. This is a DevDigest-defined gate, not a course-provided verifier, and does not establish real-provider sensitivity or the existence of eight real reviewed cases.

## Design mapping and deliberate boundaries

Manual cases must be visibly distinguished from findings-derived cases and must never count as evidence of real review decisions. Editable inputs are bounded single-file unified diffs with an anchor intersecting the new-side hunk. Store their input hash and expectation in a frozen snapshot; editing or deleting a case must not alter historical runs. Reject contradictory labels atomically under the same agent lock used by suite admission. Promotion must restore the exact tested configuration or explain why it cannot; a prompt-only update must not be represented as promotion of an entire configuration.

Promotion is admitted only for completed runs carrying a complete promotion snapshot. Store agent configuration, skill link identities and state, and hashes of skill content at admission. Under a transaction, verify that linked skills still exist with the same contents and global enabled state, reject stale agent versions and historical incomplete snapshots, then restore the agent configuration and links and create a new immutable agent version atomically. Project-context attachments are not part of evaluation; promotion must not imply they were evaluated.

The supplied screenshots cover FindingCard, Evals tab, case editor, dashboard, agent trend, and comparison. The core journey includes creation from findings, run-all for one agent, listing and comparison. The dashboard supports filtering run history by period, highlighting prompt changes and requesting runs for all agents with per-agent failure reporting. Individual case runs use a distinct frozen dataset; users may create, edit and delete cases while retaining run snapshots. Editing a finding-derived case converts it to manual provenance. A complete completed run can be promoted to a new agent version, subject to the checks above. Full-file findings follow the existing grounding gate's file-only exception; citation accuracy describes the gate, not independent proof that every cited line is accurate.

## Operational contract

- Limit each batch to 100 cases, each stored input to 256 KiB, execute one case at a time, allow no additional structured-output retries, and impose a 120-second provider timeout per case. Reject over-limit input before admission. An interrupted in-flight batch becomes failed on startup under the existing single-process model; completed results remain immutable.
- Replay a stored original or manual fragment only when its content hash matches the saved hash, together with the snapshotted agent system prompt, provider, model, strategy and resolved enabled skills. Omit dynamic repo map, project context, intent, memory and callers, and disclose the omission. The diff fingerprint and, when Git refs resolve, the immutable base/head commit IDs are recorded at review time; source content is stored only when a case is created. Recovery uses those commit IDs even after PR changes and fails if their objects are unavailable. Legacy fingerprint-only and patch-fallback reviews require current input to match the fingerprint. Run API responses omit diff text. Existing reviews without a fingerprint cannot be converted.
- Idempotency identity is workspace, original finding and decision. If the decision changes, the new decision can create a separate case; contradictory expectations for identical replay input and overlapping anchors are rejected until the prior case is removed through a future management feature.
- `POST /findings/:id/eval-cases` returns 201 for creation, 200 for the existing matching case, 404 for inaccessible IDs, 409 for an undecided finding, unavailable or changed original input or contradictory expectation, and 422 for invalid input. `GET /agents/:id/eval-cases`, `GET /agents/:id/eval-runs`, `GET /eval-runs/:id`, and `GET /eval-dashboard` return scoped data or 404. `POST /agents/:id/eval-runs` returns 202 for admission, 404 for inaccessible agent, and 409 for an empty set or an active batch; limit violations return 422. Poll the run record until terminal.
- A batch is comparable only when both batches completed and dataset fingerprint, engine version and scorer version are equal. Otherwise show raw metrics with an incompatibility explanation and no delta. Aggregate metrics are unavailable for failed or interrupted batches.
